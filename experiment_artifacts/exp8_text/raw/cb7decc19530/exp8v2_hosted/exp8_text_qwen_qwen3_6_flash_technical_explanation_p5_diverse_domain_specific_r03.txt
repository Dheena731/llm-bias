An API rate limit is a server-enforced cap on the volume of requests a client can issue within a specific time window. Rather than accepting unbounded traffic, the service counts calls against a unique identifier—typically an API key, OAuth token, or source IP—and halts processing once a predefined threshold is reached. The response returns HTTP 429 Too Many Requests, accompanied by header fields like `X-RateLimit-Remaining` and `X-RateLimit-Reset` to communicate capacity and recovery timing.

Rate limiting functions as a traffic-shaping control plane. It prevents connection pool exhaustion, guards against cascading backend failures, and preserves headroom for high-priority consumers. Under the hood, providers usually deploy fixed windows, sliding log counters, or token-bucket algorithms, each trading off memory overhead against burst tolerance. Clients are expected to implement exponential backoff with jitter, batch requests, or redistribute load across tiered keys. Poorly calibrated limits either throttle legitimate workloads or hide architectural leaks, so they’re tuned alongside caching policies, queue depths, and upstream dependency timeouts as part of system capacity design.
