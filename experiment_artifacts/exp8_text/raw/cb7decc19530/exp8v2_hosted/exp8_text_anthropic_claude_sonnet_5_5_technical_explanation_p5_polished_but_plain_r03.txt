An API rate limit is a cap on how many requests a client can send to an API within a set period of time. For example, a service might allow 100 requests per minute per user or 10,000 requests per day per account. Once a client exceeds that threshold, the API typically refuses further requests until the time window resets, often responding with an HTTP 429 status code, which means "Too Many Requests."

Providers use rate limits for several reasons. They protect servers from being overwhelmed by sudden spikes in traffic, whether accidental or malicious. They help ensure that resources are shared fairly, so one heavy user cannot degrade the experience for everyone else. They also guard against abuse such as scraping or brute-force attacks, and they give providers a way to structure pricing, with higher limits offered on paid plans.

Limits can be applied in different ways. Some are tied to an API key or user account, others to an IP address, and others to a specific endpoint that is especially expensive to run. Common techniques for enforcing them include fixed windows, which reset at regular intervals, and sliding windows or token buckets, which spread allowances more smoothly over time and permit short bursts of activity.

If you are building something that consumes an API, it helps to plan for these limits from the start. Read the provider's documentation to learn the exact thresholds, and check the response headers, which often report how many requests remain and when the limit resets. When you do hit a limit, avoid retrying immediately. Instead, wait for the period indicated in a Retry-After header if one is provided, or use exponential backoff, which increases the delay between each attempt. Caching responses, batching requests, and avoiding unnecessary calls can also keep your usage comfortably below the ceiling.
