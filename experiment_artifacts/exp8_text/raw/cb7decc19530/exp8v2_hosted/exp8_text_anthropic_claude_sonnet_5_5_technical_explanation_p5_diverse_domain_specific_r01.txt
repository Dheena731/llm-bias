An API rate limit is a cap on how many requests a client can send to a server within a set window of time. A service might allow 100 requests per minute per API key, or 5,000 per hour per IP address. Once you exceed that number, the server stops processing your calls and typically returns an HTTP 429 ("Too Many Requests") response, often with a `Retry-After` header telling you how many seconds to wait.

Providers set these limits for a few practical reasons: to keep one noisy client from starving everyone else, to contain the cost of expensive endpoints, and to blunt scraping, credential stuffing, and runaway loops in someone's buggy code. Limits are often tiered, so a free plan might get 60 calls a minute while a paid plan gets 600, and heavy endpoints like search or bulk export may have stricter caps than a simple GET on a single record.

The enforcement method affects how your client behaves. A fixed window counter resets at a boundary (say, the top of each minute), which lets a client burst at the edge of two windows. A sliding window smooths that out. A token bucket refills at a steady rate and lets you spend saved-up tokens in short bursts, which is why a client that has been idle can sometimes fire off a quick batch without being blocked.

On the client side, the usual response is to read the rate-limit headers (names vary; `X-RateLimit-Remaining` and `X-RateLimit-Reset` are common), queue or throttle outgoing calls, and retry failed ones with exponential backoff plus some random jitter so that many clients don't all retry at the same instant. Caching responses and batching requests where the API supports it will also keep you well under the ceiling.
