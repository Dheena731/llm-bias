An API rate limit is a cap on how many requests a client can send to an API within a set period of time. For example, a service might allow 100 requests per minute per user or 10,000 requests per day per application key. Once a client exceeds that allowance, the API typically rejects further requests until the time window resets, often returning an HTTP 429 status code that means "Too Many Requests."

Providers set these limits for several reasons. They protect servers from being overwhelmed by sudden spikes in traffic, whether accidental or malicious. They help ensure that one heavy user cannot degrade performance for everyone else. They also keep infrastructure costs predictable and can be used to separate pricing tiers, with higher limits offered to paying customers.

Limits can be enforced in different ways. Some use a fixed window, which counts requests within set intervals such as each minute. Others use a sliding window, which looks at the most recent stretch of time, or a token bucket, which allows short bursts of activity while still enforcing an average rate over time. Limits may apply per user, per API key, per IP address, or per endpoint, and more expensive operations often have stricter limits than simple ones.

For developers, the practical approach is to design with limits in mind. Many APIs include response headers that report how many requests remain and when the window resets, and a well-built client reads these values and slows down accordingly. When a request is rejected, the client should wait before retrying, ideally using exponential backoff, which means increasing the delay after each failed attempt. Caching responses, batching requests where the API allows it, and avoiding unnecessary polling can also reduce usage and keep an application comfortably within its allowance.
