An API rate limit is a cap on how many requests a client can send to an API within a set period of time. For example, a service might allow 100 requests per minute per user or 10,000 requests per day per application key. Once you exceed that threshold, the server typically refuses further requests until the time window resets, often returning an HTTP 429 status code that means "Too Many Requests." Many APIs also include headers in their responses that tell you how many requests you have left and when the limit will reset.

Providers set rate limits for several reasons. They protect servers from being overwhelmed by traffic spikes or runaway scripts, they keep service fair so that one heavy user cannot degrade performance for everyone else, they help defend against abuse such as scraping or denial-of-service attacks, and they allow providers to offer different pricing tiers with higher limits for paying customers.

For developers, the practical implication is to design clients that respect these limits. Common strategies include caching responses so you do not repeat identical requests, batching operations where the API allows it, spacing out calls, and handling 429 errors gracefully by waiting and retrying with exponential backoff, which means increasing the delay after each failed attempt. Reading the provider's documentation to understand the specific limits and how they are measured is an important first step when integrating with any API.
