An API rate limit is a cap on how many requests a client can send to a server within a set window of time. A service might allow 100 requests per minute per API key, or 5,000 per hour per IP address. Once you exceed the cap, the server stops doing the work and returns an error, usually HTTP 429 (Too Many Requests), often with a `Retry-After` header saying how many seconds to wait.

Providers set limits for a few practical reasons: to keep one noisy client from starving everyone else, to contain the cost of expensive queries, and to blunt scraping, credential stuffing, and runaway loops in someone's code. A script with a missing exit condition can generate thousands of calls in seconds, and a limit turns that into a failed script instead of an outage.

Limits are enforced in different ways. A fixed window counts requests per clock interval (say, per calendar minute), which is simple but allows a burst at the boundary: 100 calls at 12:00:59 and another 100 at 12:01:00. A sliding window smooths that out. A token bucket lets clients accumulate allowance and spend it in bursts, refilling at a steady rate. Some APIs also limit concurrency (how many requests can be in flight at once) or weight calls by cost, so a bulk export counts for more than a single lookup.

On the client side, the usual handling is to read the rate-limit headers when they're provided (commonly `X-RateLimit-Remaining` and `X-RateLimit-Reset`, though names vary), back off when you get a 429, and add jitter to retries so a fleet of workers doesn't all wake up and hit the server at the same instant. Caching responses and batching requests where the API supports it reduces how often you approach the limit at all.
